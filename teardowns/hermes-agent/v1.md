## 1. Executive Summary

Hermes Agent is an open-source, self-hosted AI agent framework from Nous Research that turns LLMs into persistent, tool-using assistants with a closed learning loop. Unlike simple chatbot wrappers, Hermes implements a full agent runtime with SQLite-backed session persistence, bounded curated memory, autonomous skill creation, context compression with structured summaries, multi-provider failover, six terminal backends, and an RL training environment framework — making it both a practical assistant and a research platform for training the next generation of tool-calling models.

This document is a technical deep dive into how Hermes works — the software architecture decisions, data flows, and design tradeoffs that make a stateless LLM behave like a continuously-learning, self-improving assistant.

## 3. The Agent Loop — The Core Engine

The heart of Hermes is `AIAgent` in `run_agent.py` — a synchronous orchestration engine that handles prompt construction, model calls, tool execution, retries, compression, and persistence.

### 3.1 Turn Lifecycle

```
run_conversation()
  → Generate effective task_id
  → Append current user message
  → Load or build cached system prompt
  → Maybe preflight-compress (if approaching token limit)
  → Build api_messages (conversation history)
  → Inject ephemeral prompt layers
  → Apply prompt caching (Anthropic cache_control breakpoints)
  → Make interruptible API call
  → If tool_calls: execute tools → append results → LOOP BACK
  → If final text: persist → cleanup → return response
```

### 3.2 Three API Modes

Hermes doesn't treat all providers the same. It resolves to one of three execution modes:

| API Mode | Used For |
|----------|----------|
| `chat_completions` | OpenAI-compatible endpoints (OpenRouter, custom, most providers) |
| `codex_responses` | OpenAI Codex / Responses API |
| `anthropic_messages` | Native Anthropic Messages API (with prompt caching) |

Mode is resolved from explicit args, provider selection, and base URL heuristics — ensuring the right wire format and authentication for each provider.

### 3.3 Interruptible API Calls

Hermes wraps every API request so it can be interrupted mid-flight. This is critical because:
- The agent may be in a long LLM call (minutes for complex tool-use chains)
- The user may send a new message or `/stop`
- The gateway may need cancellation semantics for session management

### 3.4 Budget Tracking & Fallback

Hermes tracks a **shared iteration budget** across parent and sub-agents. Near the budget limit, it injects pressure hints that tell the model to wrap up.

**Fallback model support**: When the primary model fails (401, 403, 429, 500+), Hermes can automatically switch to a configured fallback provider/model. The swap is in-place — same session, same context, different endpoint:

```
Primary fails (HTTP 429) → _try_activate_fallback()
  → resolve_provider_client() for fallback
  → Swap model, provider, base_url, api_mode, client
  → Reset retry counter → Continue loop
```

Fallback fires once per session (no cascading failures).

### 3.5 Callback Surfaces

AIAgent supports rich streaming callbacks:
- `tool_progress_callback` — tool execution progress
- `thinking_callback` — model reasoning/thinking content
- `stream_delta_callback` — streaming text deltas
- `step_callback` — major step transitions
- `clarify_callback` — interactive clarification flows
- `status_callback` — status updates
- `tool_gen_callback` — tool generation events

These callbacks are how the CLI, gateway, and ACP integrations deliver real-time streaming and interactive approval flows to different surfaces.

## 4. Prompt Assembly — Cached + Ephemeral Split

This is one of the most important design decisions in Hermes. The prompt is split into two categories: **cached layers** (stable across turns, optimized for LLM prefix caching) and **ephemeral layers** (injected at API-call time, never persisted).

### 4.1 Cached System Prompt Layers

Assembled in this order:

```
Layer 1:  Agent identity (SOUL.md or DEFAULT_AGENT_IDENTITY)
Layer 2:  Tool-aware behavior guidance
Layer 3:  Honcho static block (when active)
Layer 4:  Optional system message (from config or API)
Layer 5:  Frozen MEMORY snapshot (with capacity header: "67% — 1,474/2,200 chars")
Layer 6:  Frozen USER profile snapshot
Layer 7:  Skills index (compact metadata list)
Layer 8:  Context files (AGENTS.md / .hermes.md / CLAUDE.md / .cursorrules)
Layer 9:  Timestamp + session ID
Layer 10: Platform hint ("CLI AI Agent" / "messaging" etc.)
```

**Key architectural decisions:**

- **SOUL.md** is loaded as Layer 1 (identity). If present, `build_context_files_prompt(skip_soul=True)` prevents it from appearing twice.
- **Memory is a frozen snapshot** — injected at session start, never mutated mid-session. Tool writes update disk immediately but don't change the prompt until next session.
- **Context file priority** (first match wins): `.hermes.md` → `AGENTS.md` → `CLAUDE.md` → `.cursorrules`
- All context files are **security scanned** (invisible Unicode, prompt injection, credential exfiltration) and **truncated** (20K chars, 70/20 head/tail ratio).

### 4.2 Ephemeral Layers (API-Call-Time Only)

These are intentionally NOT persisted:
- `ephemeral_system_prompt`
- Prefill messages
- Gateway session context overlays
- Honcho recall injected into current-turn user message

**Why this split matters:** The stable prefix preserves provider-side prompt caching. Moving anything dynamic into the cached prompt would invalidate the cache on every turn.

### 4.3 Anthropic Prompt Caching

Hermes implements Anthropic's `cache_control` breakpoints (max 4 per request):

```
Breakpoint 1: System prompt                  ← Stable across all turns
Breakpoint 2: 3rd-to-last non-system message ┐
Breakpoint 3: 2nd-to-last non-system message ├─ Rolling window
Breakpoint 4: Last non-system message        ┘
```

**Result:** ~75% input token cost reduction on multi-turn conversations. TTL configurable: 5m (default) or 1h for long sessions. Automatically enabled for Claude models.

## 5. Session Storage — SQLite with WAL

Hermes stores all session data in a single SQLite database (`~/.hermes/state.db`) using WAL mode for concurrent read/write access.

### 5.1 Schema

```
~/.hermes/state.db (SQLite, WAL mode)
├── sessions          Session metadata, token counts, billing, lineage
│   ├── id, source, user_id, model, model_config
│   ├── parent_session_id              ← Compression lineage chains
│   ├── input_tokens, output_tokens    ← Per-session token accounting
│   ├── cache_read_tokens, cache_write_tokens, reasoning_tokens
│   ├── estimated_cost_usd, actual_cost_usd, cost_status
│   └── title (unique non-NULL)
│
├── messages          Full message history per session
│   ├── session_id, role, content, timestamp
│   ├── tool_call_id, tool_calls (JSON), tool_name
│   ├── finish_reason, token_count
│   └── reasoning, reasoning_details, codex_reasoning_items
│
├── messages_fts      FTS5 virtual table for full-text search
│   └── Kept in sync via INSERT/UPDATE/DELETE triggers
│
└── schema_version    Migration tracking (currently v6)
```

### 5.2 Write Contention Handling

Multiple processes (gateway + CLI + ACP + subagents) share one database. Hermes handles contention with:

- **Short SQLite timeout** (1s instead of default 30s)
- **Application-level retry**: 15 retries, 20-150ms random jitter
- **`BEGIN IMMEDIATE` transactions**: surface lock contention at transaction start
- **Periodic WAL checkpoints**: every 50 writes (PASSIVE mode)

This avoids the "convoy effect" where SQLite's deterministic backoff causes all writers to retry at the same intervals.

### 5.3 Full-Text Search (FTS5)

Every message is automatically indexed in an FTS5 virtual table via triggers:

```sql
-- Search with FTS5 syntax
SELECT * FROM messages_fts WHERE messages_fts MATCH 'docker deployment';

-- Supports: keywords, "exact phrase", OR, NOT, prefix*
-- Filtered by source, role, exclude_sources
```

FTS5 powers `session_search` — the agent's ability to recall past conversations. Results include FTS5-generated snippets with match highlighting.

### 5.4 Session Lineage

When context compression triggers a session split, the new session links to the old one via `parent_session_id`. This creates traceable compression chains:

```
sess_abc123 → (compressed) → sess_def456 → (compressed) → sess_ghi789
```

Recursive CTEs can walk the entire lineage forward or backward.

## 6. Memory Architecture — Bounded Curation

### 6.1 Two-File Bounded Memory

```
┌─────────────────────────────────────────────────────────┐
│  MEMORY.md — Agent's personal notes                     │
│  2,200 chars (~800 tokens) · Hard limit                 │
│  Environment facts, conventions, lessons learned        │
├─────────────────────────────────────────────────────────┤
│  USER.md — User profile                                 │
│  1,375 chars (~500 tokens) · Hard limit                 │
│  Preferences, communication style, identity             │
└─────────────────────────────────────────────────────────┘
```

Both stored in `~/.hermes/memories/`. Managed exclusively via the `memory` tool:

| Action | Behavior |
|--------|----------|
| `add` | Append a new entry |
| `replace` | Substring-match an existing entry, replace it |
| `remove` | Substring-match an existing entry, delete it |

**There is no `read` action** — memory is automatically injected into the system prompt.

### 6.2 Frozen Snapshot Pattern

Memory is captured once at session start and rendered into the prompt with capacity metadata:

```
══════════════════════════════════════════════
MEMORY (your personal notes) [67% — 1,474/2,200 chars]
══════════════════════════════════════════════
User's project is a Rust web service at ~/code/myapi using Axum + SQLx
§
This machine runs Ubuntu 22.04, has Docker and Podman installed
§
User prefers concise responses, dislikes verbose explanations
```

Mid-session memory writes update disk immediately but DON'T change the prompt until the next session. This is intentional — it preserves the LLM's prefix cache.

### 6.3 Capacity Management

When memory is full, the tool returns an error with current entries and usage. The agent must consolidate or replace entries to make room. The capacity header in the prompt (`[67% — 1,474/2,200 chars]`) gives the model continuous awareness of remaining capacity.

**Security scanning**: All memory writes are scanned for prompt injection patterns, credential exfiltration attempts, and invisible Unicode before acceptance.

### 6.4 Cross-Session Recall (session_search)

Beyond bounded memory, the agent can search ALL past conversations:

```
session_search("docker deployment error")
  → FTS5 query across messages table
  → Results summarized by auxiliary LLM (Gemini Flash)
  → Returns relevant past conversations with snippets
```

| Feature | MEMORY.md | session_search |
|---------|-----------|----------------|
| Capacity | ~800 tokens | Unlimited (all sessions) |
| Speed | Instant (in system prompt) | Search + LLM summarization |
| Token cost | Fixed per session | On-demand |
| Management | Manually curated | Automatic |

### 6.5 Honcho — AI-Native User Modeling

For deeper cross-session understanding, Hermes integrates with [Honcho](https://honcho.dev) — a dual-peer memory system that learns user preferences, goals, and communication style via dialectic reasoning.

**Dual-peer architecture:**
- **User peer** — observed from user messages (preferences, goals, style)
- **AI peer** — observed from assistant messages (knowledge, behavior patterns)

Both representations are injected into the system prompt when available.

**Async context pipeline:**
```
Turn N-1 completes → Background: prefetch Honcho context for Turn N
Turn N starts → Consume cached Honcho context (zero HTTP latency)
```

Turn 1 is a cold start (no cache). All subsequent turns use prefetched results.

**Memory modes:**
- `hybrid` (default): Both Honcho and local files (MEMORY.md + USER.md)
- `honcho`: Honcho only, skip local file writes

**Dynamic reasoning level:** Dialectic query effort scales with message complexity:
- <120 chars → config default (typically `low`)
- 120-400 chars → one level above default
- >400 chars → two levels above default

**Gateway integration:** Honcho managers persist at the gateway session layer, not the ephemeral AIAgent layer. Each platform chat gets its own Honcho session context, threaded through the entire tool dispatch chain.

## 7. Context Compression — Dual-Layer System

Hermes has two independent compression layers that work together:

```
┌──────────────────────────┐
│ Gateway Session Hygiene  │  Fires at 85% of context
│ (pre-agent, rough est.)  │  Safety net for large sessions
└─────────────┬────────────┘
              │
              ▼
┌──────────────────────────┐
│ Agent ContextCompressor  │  Fires at 50% of context (default)
│ (in-loop, real tokens)   │  Normal context management
└──────────────────────────┘
```

### 7.1 Configuration

```yaml
compression:
  enabled: true
  threshold: 0.50     # Fraction of context window
  target_ratio: 0.20  # How much of threshold to keep as tail
  protect_last_n: 20  # Minimum protected tail messages
  summary_model: null  # Override model for summaries
```

### 7.2 Four-Phase Algorithm

**Phase 1: Prune Old Tool Results** (cheap, no LLM call)
Old tool results (>200 chars) outside the protected tail replaced with:
`[Old tool output cleared to save context space]`

**Phase 2: Determine Boundaries**
```
[0..2]    ← protect_first_n (system + first exchange)
[3..N]    ← middle turns → SUMMARIZED
[N..end]  ← tail (by token budget OR protect_last_n)
```
Boundaries aligned to avoid splitting tool_call/tool_result groups via `_align_boundary_backward()`.

**Phase 3: Generate Structured Summary**
The middle turns are summarized using an auxiliary LLM with this template:

```markdown
## Goal
[What the user is trying to accomplish]

## Constraints & Preferences
[User preferences, coding style, important decisions]

## Progress
### Done
[Completed work — specific file paths, commands, results]
### In Progress
[Work currently underway]
### Blocked
[Any blockers or issues]

## Key Decisions
[Important technical decisions and why]

## Relevant Files
[Files read, modified, or created]

## Next Steps
[What needs to happen next]

## Critical Context
[Specific values, error messages, configuration details]
```

Summary token budget: `content_tokens × 0.20` (min 2K, max min(context × 0.05, 12K)).

**Phase 4: Assemble Compressed Messages**
Head + summary + tail. Orphaned tool pairs cleaned by `_sanitize_tool_pairs()`.

### 7.3 Iterative Re-compression

On subsequent compressions, the previous summary is passed with "update, don't re-summarize" instructions. Information evolves: items move from "In Progress" to "Done", obsolete context is removed, new progress is added.

### 7.4 Context Pressure Warnings

```
⚠️ Context is 85% to compaction threshold (42,500/50,000 tokens)
```

Fires at 85% of the compression threshold (not 85% of context). Cleared after successful compression.

## 8. Tool System — Self-Registering Registry

### 8.1 Registration Model

Each tool module calls `registry.register()` at import time:

```python
registry.register(
    name="terminal",
    toolset="terminal",
    schema={...},                    # OpenAI function-calling schema
    handler=handle_terminal,         # Execution function
    check_fn=check_terminal,         # Availability gate (returns True/False)
    requires_env=["SOME_VAR"],       # For UI display
    is_async=False,
    description="Run commands",
    emoji="💻",
)
```

### 8.2 Discovery Pipeline

```python
_discover_tools()
  → Import 20+ tool modules (each triggers registry.register())
  → Catch errors in optional tools (missing deps don't block other tools)
  → Discover MCP tools (from MCP server configs)
  → Discover plugin tools (user/project/pip plugins)
```

### 8.3 Toolset Resolution

Toolsets are named bundles resolved through:
- Explicit enabled/disabled lists
- Platform presets: `hermes-cli`, `hermes-telegram`, `hermes-acp`, etc.
- Dynamic MCP toolsets
- Legacy name mapping for backward compatibility

**Schema patching**: After filtering, `execute_code` and `browser_navigate` schemas are dynamically adjusted to only reference tools that passed filtering (prevents model hallucination of unavailable tools).

### 8.4 Dispatch Flow

```
Model returns tool_call
  → handle_function_call()
  → [Agent-loop tools?] → handled directly (todo, memory, session_search, delegate)
  → [Plugin pre-hook] → invoke_hook("pre_tool_call")
  → registry.dispatch(name, args)
  → [Async handler?] → bridge via _run_async()
  → [Sync handler?] → call directly
  → Return result string (or JSON error)
  → [Plugin post-hook] → invoke_hook("post_tool_call")
```

**Error wrapping** at two levels ensures the model always receives well-formed JSON, never an unhandled exception.

### 8.5 Dangerous Command Approval

The terminal tool integrates a pattern-based approval system:

```
Command entered → detect_dangerous_command() checks DANGEROUS_PATTERNS
  → No match → Execute immediately
  → Match found:
    → CLI: interactive prompt [once | session | always | deny]
    → Gateway: async approval via messaging platform
    → Smart mode: auxiliary LLM assesses risk, auto-approve/deny/escalate
```

**35+ dangerous patterns** including: `rm -rf`, `mkfs`, `dd if=`, `DROP TABLE`, `DELETE FROM` (without WHERE), `curl | sh`, `chmod 777`, `kill -9 -1`, `systemctl stop`, fork bombs, and more.

**Smart approval mode**: An auxiliary LLM evaluates context — `rm -rf node_modules/` matches "recursive delete" but is safe, so it's auto-approved. Genuinely dangerous commands are auto-denied. Uncertain cases escalate to manual prompt.

**Permanent allowlist**: "always" approvals persist to `config.yaml` → loaded at startup, never re-prompted.

### 8.6 Agent-Loop Tools

Four tools are intercepted before registry dispatch because they need agent-level state:

| Tool | Purpose | Why Special |
|------|---------|-------------|
| `todo` | Planning/task tracking | Needs TodoStore |
| `memory` | Persistent memory writes | Needs MemoryStore |
| `session_search` | Cross-session recall | Needs SessionDB |
| `delegate_task` | Spawns subagent sessions | Needs AIAgent orchestration |

Their schemas are still in the registry (for `get_tool_definitions()`), but handlers return stub errors if dispatch reaches them directly.

## 9. Terminal & Execution Environments

### 9.1 Six Backends

| Backend | Description | Persistence | Cost Model |
|---------|-------------|-------------|------------|
| **Local** | Direct host execution | Always on | Free |
| **Docker** | Container isolation | Ephemeral | Free (local) |
| **SSH** | Remote host execution | Remote state | VPS cost |
| **Daytona** | Serverless workspace | Hibernates when idle | Pay-per-use |
| **Modal** | Serverless cloud | Ephemeral per-job | Pay-per-use |
| **Singularity** | HPC container | Shared filesystem | HPC allocation |

**Daytona and Modal** offer **serverless persistence** — the agent's environment hibernates when idle and wakes on demand, costing nearly nothing between sessions. Run Hermes on a $5 VPS or a GPU cluster.

### 9.2 Per-Task CWD Overrides

Terminal tools support scoped working directory overrides (used by ACP for editor workspace binding and by sub-agents for isolated workspaces).

### 9.3 Background Process Management

Long-running processes can be started, tracked, and queried across turns — similar to OpenClaw's `process` tool.

## 10. Skills System — Self-Improving Procedural Memory

### 10.1 Progressive Disclosure

Skills use a token-efficient loading pattern:

```
Level 0: skills_list()           → [{name, description, category}]  (~3K tokens)
Level 1: skill_view(name)        → Full SKILL.md content + metadata
Level 2: skill_view(name, path)  → Specific reference file
```

The agent only loads full skill content when the task matches. This keeps prompt overhead minimal.

### 10.2 SKILL.md Format

```yaml
---
name: my-skill
description: Brief description
version: 1.0.0
platforms: [macos, linux]          # OS restrictions
metadata:
  hermes:
    tags: [python, automation]
    category: devops
    fallback_for_toolsets: [web]   # Conditional activation
    requires_toolsets: [terminal]
---
# Skill Title
## When to Use
## Procedure
## Pitfalls
## Verification
```

### 10.3 Conditional Activation

Skills can automatically show or hide based on available tools:

| Field | Behavior |
|-------|----------|
| `fallback_for_toolsets: [web]` | Hidden when web tools available, shown when missing |
| `requires_toolsets: [terminal]` | Hidden when terminal unavailable |

Example: The built-in `duckduckgo-search` skill hides itself when `FIRECRAWL_API_KEY` is set (premium web search available). When the key is missing, it appears as a fallback.

### 10.4 Autonomous Skill Creation & Self-Improvement

**This is unique to Hermes.** After solving a complex task, the agent can:
1. Autonomously create a new skill from the experience
2. Save it to `~/.hermes/skills/` as a proper SKILL.md
3. Self-improve skills during subsequent use

This creates a **closed learning loop** — the agent gets better at tasks it has done before, without any manual intervention.

### 10.5 Secure Setup on Load

Skills can declare required environment variables. When accessed for the first time (CLI only — never in messaging), Hermes prompts securely. Declared vars are automatically passed through to execute_code and terminal sandboxes.

## 11. Messaging Gateway

### 11.1 Core Architecture

The gateway is a long-running Python process that connects Hermes to external platforms:

```
Incoming platform event
  → Platform adapter normalizes message
  → _is_user_authorized() checks allowlists/pairing
  → Session routing (by platform + user + thread)
  → Dispatch to AIAgent instance
  → Delivery routing (origin chat, home channel, explicit target)
```

### 11.2 Session Routing

Session keys depend on:
- Platform (telegram, discord, slack, etc.)
- User/chat identity
- Thread/topic identity
- Platform-specific routing behavior

### 11.3 Authorization Model

Checked in order:
1. Per-platform allow-all flag
2. DM pairing approved list
3. Platform-specific allowlists
4. Global allowlist
5. Global allow-all
6. **Default: deny**

### 11.4 DM Pairing

Code-based pairing for flexible authorization:
1. Unknown user sends DM → bot replies with 8-char pairing code
2. Owner runs `hermes pairing approve telegram ABC12DEF`
3. User permanently approved

Security: cryptographic randomness, 1-hour TTL, rate limiting (1 req/user/10min), max 3 pending codes, 5-failure lockout.

### 11.5 Background Maintenance

The gateway also runs:
- Cron ticking
- Cache refreshes
- Session expiry checks
- Proactive memory flush before reset/expiry
- Honcho session management

## 12. Cron — Agent-Native Scheduling

Cron jobs in Hermes are first-class agent tasks, not shell crontabs.

### 12.1 Model-Facing Interface

A single `cronjob` tool with actions: `create`, `list`, `update`, `pause`, `resume`, `run`, `remove`.

### 12.2 Scheduling Types

- One-shot delays
- Intervals
- Cron expressions
- Explicit timestamps

### 12.3 Skill-Backed Jobs

A cron job can attach multiple skills. At runtime, skills are loaded in order, then the job prompt is appended. This gives scheduled jobs reusable guidance without pasting full skill bodies into the prompt.

### 12.4 Safety: Recursion Guard

Cron-run sessions **disable the cronjob toolset**. This prevents scheduled jobs from recursively creating more cron jobs — avoiding token explosion and scheduler overload.

### 12.5 Delivery

Jobs can deliver to: origin chat, local files, platform home channels, explicit platform/chat IDs.

### 12.6 Locking

Lock-based protection ensures overlapping scheduler ticks don't execute the same due-job batch twice.

## 13. Sub-Agent Architecture

### 13.1 Delegation Pattern

```
Main agent → delegate_task("Research X")
               → Spawns isolated AIAgent
               → Own context window, own tool execution
               → Returns result to parent context
```

### 13.2 Shared Budget

Parent and sub-agents share an iteration budget. Budget pressure hints inject near the limit to force convergence.

### 13.3 Key Constraints

- Sub-agents inherit the parent's provider but NOT the fallback config
- Restricted tool sets (no recursive delegation)
- Can use different models via explicit configuration

## 14. ACP — Editor Integration

Hermes exposes itself as an editor-native agent via ACP (Agent Communication Protocol) over stdio/JSON-RPC.

### 14.1 Architecture

```
Editor (VS Code / Cursor / etc.)
  ← stdio/JSON-RPC →
HermesACPAgent (acp_adapter/server.py)
  → SessionManager (per-editor-session)
  → AIAgent (sync, in ThreadPoolExecutor)
  → Event bridge (callbacks → ACP session_update events)
  → Permission bridge (dangerous commands → ACP approval requests)
```

### 14.2 Key Design

- **Sync-to-async bridge**: AIAgent is synchronous; ACP I/O is async. The event bridge uses `asyncio.run_coroutine_threadsafe()` from worker threads.
- **Working directory binding**: ACP sessions carry an editor CWD, scoped to the session ID via terminal/file overrides.
- **Tool rendering**: Hermes tools are mapped to ACP tool kinds — `patch`/`write_file` → file diffs, `terminal` → shell command text.
- **Duplicate same-name calls**: Event bridge tracks tool IDs FIFO per tool name (not just one ID per name) for correct parallel/repeated dispatch.

## 15. Provider Runtime Resolution

### 15.1 Shared Resolver

One resolver used by CLI, gateway, cron, ACP, and auxiliary calls:

```
Resolution precedence:
  1. Explicit CLI/runtime request
  2. config.yaml model/provider config
  3. Environment variables
  4. Provider-specific defaults / auto-resolution
```

Saved model/provider choice is the source of truth — prevents stale shell exports from silently overriding the selected endpoint.

### 15.2 API Key Scoping

Hermes prevents leaking the wrong API key to a custom endpoint:
- `OPENROUTER_API_KEY` → only sent to openrouter.ai
- `AI_GATEWAY_API_KEY` → only sent to ai-gateway.vercel.sh
- `OPENAI_API_KEY` → custom endpoints and fallback

### 15.3 Auxiliary Model Routing

Auxiliary tasks (vision, compression summaries, session search, skills hub, MCP helpers, memory flushes) can use their own provider/model routing, independent of the main conversational model.

## 18. What Makes This Architecture Interesting (For Architects)

### 18.1 Bounded Memory Forces Curation

By hard-capping memory at ~1,300 tokens total, Hermes forces the model to make curation decisions. This is counterintuitive — why limit what the agent can remember? Because unbounded memory leads to prompt bloat and stale information. The capacity header (`67% — 1,474/2,200 chars`) gives the model continuous awareness, turning memory management into an optimization problem the model solves itself.

### 18.2 Cached/Ephemeral Prompt Split

The deliberate separation between cached and ephemeral prompt layers is a performance architecture decision, not just an organizational one. It directly enables Anthropic's prompt caching (~75% cost reduction) while keeping the agent loop simple. Most agent frameworks don't make this distinction.

### 18.3 Dual-Layer Compression

Having both a gateway safety net (85% threshold, rough estimate) and an agent-level compressor (50% threshold, real tokens) provides defense in depth. Sessions that escape normal compression (overnight accumulation in messaging) are caught before they cause API failures.

### 18.4 Structured Summary Templates

Compression summaries follow a fixed template (Goal/Progress/Decisions/Files/Next Steps). This produces dramatically more useful compressions than freeform summaries — the model can pick up where it left off with structured context instead of a narrative blob.

### 18.5 Self-Registering Tool Architecture

Tools declare themselves at import time via `registry.register()`. This means adding a tool is a single file with no framework wiring. The check_fn pattern enables graceful degradation — tools with missing dependencies simply don't appear.

### 18.6 The Agent as a Research Platform

Hermes' environment framework, trajectory generation, and Atropos RL integration mean the same codebase that runs your personal assistant can also generate training data for the next generation of models. The tool-calling pipeline is both a product and a research instrument.

### 20.2 Parallel Tool Execution — Path-Scoped Safety Analysis

The docs say "concurrent execution for multiple non-interactive tools" but the source reveals a sophisticated safety analysis before parallelizing:

```python
_NEVER_PARALLEL_TOOLS = frozenset({"clarify"})

_PARALLEL_SAFE_TOOLS = frozenset({
    "ha_get_state", "ha_list_entities", "ha_list_services",
    "honcho_context", "honcho_profile", "honcho_search",
    "read_file", "search_files", "session_search",
    "skill_view", "skills_list", "vision_analyze",
    "web_extract", "web_search",
})

_PATH_SCOPED_TOOLS = frozenset({"read_file", "write_file", "patch"})
```

**Path-scoped concurrency**: File tools (`read_file`, `write_file`, `patch`) can run in parallel *only if their target paths don't overlap*. The `_paths_overlap()` function checks whether two file paths share a common ancestor subtree. If `write_file("/app/src/main.py")` and `write_file("/app/src/utils.py")` are in the same batch — parallel. If `write_file("/app/src/main.py")` and `patch("/app/src/main.py")` — sequential.

**Arg parse failure → sequential**: If tool call arguments can't be JSON-parsed or aren't a dict, the entire batch falls back to sequential execution (fail-safe).

Max concurrent workers: 8 threads (`_MAX_TOOL_WORKERS = 8`).

### 20.3 Credential Pool — Multi-Key Rotation & Failover

The `agent/credential_pool.py` implements a full credential management system not described in the docs:

**Pool strategies:**
- `fill_first` — use one key until exhausted
- `round_robin` — rotate through keys
- `random` — random selection
- `least_used` — pick the least-used credential

**Automatic rotation on API errors:**
- **HTTP 402** (billing exhaustion): immediately rotate to next credential
- **HTTP 429** (rate limit): retry once with same key, then rotate on second 429
- **HTTP 401** (auth failure): attempt token refresh first, then rotate if refresh fails

**Cooldown timers:**
- 429 exhaustion: 1-hour cooldown before retrying that credential
- 402/other exhaustion: 24-hour cooldown

This means Hermes can be configured with multiple API keys for the same provider and automatically failover between them during rate limits or billing issues.

### 20.4 Smart Model Routing — Cheap vs. Strong

`agent/smart_model_routing.py` implements **per-turn model routing** that downgrades simple messages to a cheaper model:

**Classification heuristic** (conservative — errs toward the strong model):
- Message > 160 chars → strong model
- Message > 28 words → strong model
- Contains code fences, URLs, or newlines → strong model
- Contains keywords like `debug`, `implement`, `refactor`, `analyze`, `test`, `plan`, `docker` → strong model

Simple messages ("what's the weather?", "thanks", "yes") route to a configured cheap model. This saves cost on conversational turns that don't need frontier reasoning.

### 20.5 Background Memory/Skill Review — The Learning Loop Internals

The docs mention "autonomous skill creation" but the source reveals the exact mechanism:

**Two separate nudge counters:**
- `_memory_nudge_interval = 10` (default: every 10 user turns)
- `_skill_nudge_interval = 10` (default: every 10 tool iterations)

**After a response is delivered** (never during), if either counter fires:
1. A background thread spawns a **forked AIAgent** with the same model and tools
2. The fork receives the full conversation history + a review prompt
3. Three review prompts exist:
   - **Memory-only**: "Has the user revealed preferences, persona, personal details?"
   - **Skill-only**: "Was a non-trivial approach used with trial-and-error?"
   - **Combined**: Both checks in one prompt
4. The fork runs silently (stdout/stderr → /dev/null), max 8 iterations
5. Successful memory/skill writes are surfaced as: `💾 Memory updated · Skill created`
6. The fork's OpenAI client is explicitly closed to avoid "Event loop is closed" errors during GC

**Critical detail**: The review runs AFTER the response is delivered, so it never competes with the user's task for model attention. The nudge counters reset after each review, and the background thread is daemon (dies with the process).

### 20.6 Tirith Security Scanner — Pre-Execution Threat Detection

`tools/tirith_security.py` wraps an external binary (`tirith`) for content-level threat scanning before command execution:

- **Scans for**: homograph URLs, pipe-to-interpreter patterns, terminal injection, suspicious content
- **Verdicts**: exit 0 = allow, exit 1 = block, exit 2 = warn
- **Auto-install**: if `tirith` isn't found, it's downloaded from GitHub releases with SHA-256 checksum verification. When `cosign` is available, supply-chain provenance (GitHub Actions workflow signature) is also verified.
- **Fail-open configurable**: operational failures (spawn error, timeout) can be configured to allow or block

This is a layer beyond the DANGEROUS_PATTERNS regex — it catches content-level threats that pattern matching would miss.

### 20.7 Checkpoint Manager — Transparent Filesystem Snapshots

`tools/checkpoint_manager.py` creates automatic git-based snapshots of working directories:

```
~/.hermes/checkpoints/{sha256(abs_dir)[:16]}/   — shadow git repo
    HEAD, refs/, objects/                        — standard git internals
    HERMES_WORKDIR                               — original dir path
    info/exclude                                 — default excludes
```

- **Not a tool** — the LLM never sees it. It's transparent infrastructure.
- **Triggers**: automatic snapshot before file-mutating operations (`write_file`, `patch`), once per conversation turn
- **Provides rollback**: to any previous checkpoint
- **Shadow repo**: uses `GIT_DIR` + `GIT_WORK_TREE` so no git state leaks into the user's project

**Scans for**: data exfiltration, prompt injection, destructive commands, persistence mechanisms.

### 20.12 URL Safety — SSRF Prevention

`tools/url_safety.py` blocks requests to private/internal network addresses:

- Vision tools have an httpx event hook that re-validates each redirect target

### 20.14 Trajectory Compressor — Training Data Pipeline

`trajectory_compressor.py` (1,518 lines) post-processes agent trajectories to compress them within a target token budget while preserving training signal quality:

**Compression strategy:**
1. Protect first turns (system, human, first gpt, first tool)
2. Protect last N turns (final actions and conclusions)
3. Compress MIDDLE turns only, starting from 2nd tool response
4. Replace compressed region with a single human summary message
5. Keep remaining tool calls intact

**Default target**: 15,250 tokens. Uses Gemini Flash for summarization. Supports sampling (e.g., compress 15% of a dataset for quick iteration).

All computed from the SQLite state database.

### 20.16 Destructive Command Detection for Parallel Safety

Beyond the approval system's DANGEROUS_PATTERNS, the parallel tool executor has its own `_DESTRUCTIVE_PATTERNS` regex that checks terminal commands for file-modifying operations:

```python
_DESTRUCTIVE_PATTERNS = re.compile(
    r"""(?:^|\s|&&|\|\||;|`)(?:
        rm\s|rmdir\s|mv\s|sed\s+-i|truncate\s|
        dd\s|shred\s|git\s+(?:reset|clean|checkout)\s
    )""", re.VERBOSE,
)
```

Plus a `_REDIRECT_OVERWRITE` pattern for `>` (but not `>>`). Terminal commands matching these patterns are never parallelized — they always run sequentially, even if the parallel safety analysis would otherwise allow them.

### 20.17 Tool Call Deduplication & Repair

Two undocumented safety mechanisms in the agent loop:

**`_deduplicate_tool_calls()`**: When the model generates duplicate tool calls (same function + same arguments), only the first is kept. Prevents wasted execution.

**`_repair_tool_call()`**: When a tool call fails due to malformed arguments, Hermes attempts to repair it — e.g., fixing JSON syntax errors or extracting the intended function name from garbled output.

**`_cap_delegate_task_calls()`**: Limits the number of `delegate_task` calls in a single batch, preventing sub-agent fan-out explosions.

### 20.18 Budget Pressure System

The docs mention "budget pressure hints" — the source reveals a two-tier system:

```python
_budget_caution_threshold = 0.7   # 70% — nudge to start wrapping up
_budget_warning_threshold = 0.9   # 90% — urgent, respond now
```

At 70% of iteration budget: gentle nudge to consolidate work.
At 90%: urgent directive to produce a final response.

Budget warnings are **stripped from history** (`_strip_budget_warnings_from_history()`) before the next turn so they don't pollute the conversation context.

### 20.19 Deterministic Tool Call IDs

`_deterministic_call_id()` generates reproducible tool call IDs from the function name + arguments + index. This matters for Codex Responses API mode where tool call IDs need to be consistent across retry attempts — without deterministic IDs, retries would create orphaned tool results.

### 20.20 Safe Stdio Wrapper

`_SafeWriter` wraps stdout/stderr to catch `BrokenPipeError` and `UnicodeEncodeError` silently. This prevents the agent from crashing when piped to processes that close early or when terminal encoding doesn't support the output characters. Installed globally at module load via `_install_safe_stdio()`.

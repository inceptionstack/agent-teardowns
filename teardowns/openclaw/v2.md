## 1. Executive Summary

OpenClaw is an open-source, self-hosted AI agent framework that turns large language models into persistent, tool-using assistants with real-world integrations. It implements a full agent runtime with session management, memory persistence, context window optimization, 30+ messaging channels, sandboxed tool execution, MCP server support, OpenAI-compatible HTTP APIs, background task orchestration, event-driven extensibility via 20+ hook types, and native mobile apps for iOS, macOS, and Android.

This document is a technical deep dive based on direct source code analysis of the v2026.4.1 codebase (~8,700 TypeScript source files, 90 extension packages, 53 bundled skills).

## 4. The Gateway — The Central Nervous System

The Gateway is a single long-lived Node.js daemon (v22.12+) that owns all state and connections. It runs as a systemd/launchd/schtasks service.

**Source:** `src/gateway/server.impl.ts` (58k lines — the single largest file in the codebase)

### 4.1 WebSocket-First Protocol

**Source:** `src/gateway/protocol/schema/frames.ts`

The Gateway exposes a typed WebSocket API (default `127.0.0.1:18789`). Wire protocol:

- **RequestFrame**: `{type:"req", id, method, params}`
- **ResponseFrame**: `{type:"res", id, ok, payload|error}`
- **EventFrame**: `{type:"event", event, payload, seq?, stateVersion?}`

**149 gateway methods** organized into domains:
- `agents.*` — agent CRUD
- `chat.*` — send, abort, history
- `sessions.*` — list, create, send, patch, reset, compact
- `cron.*` — list, add, update, remove, run, runs
- `node.*` — list, invoke, pair
- `device.*` — pair, token
- `exec.approval.*` — approval lifecycle
- `plugin.approval.*` — plugin approval lifecycle
- `config.*` — get, set, apply, patch, schema
- `skills.*` — status, bins, install, update
- `talk.*` — TTS config, speak, mode
- `health`, `status`, `usage.*` — monitoring
- `channels.*` — status, logout

**14 event types** including `agent`, `chat`, `session.message`, `session.tool`, `presence`, `tick`, `shutdown`, `heartbeat`, `cron`, and approval events.

**Connection handshake:**
1. Server sends `connect.challenge` with nonce
2. Client sends `ConnectParams` with auth (token/password/device-token/bootstrap-token)
3. Server responds with `hello-ok` containing protocol version, server version, available methods/events, policy parameters, and device token

### 4.2 Device Pairing & Trust Model

**Source:** `src/pairing/pairing-store.ts` (27k), `pairing-challenge.ts`, `setup-code.ts`

### 4.3 Authentication

**Source:** `src/gateway/auth.ts` (18k), `auth-rate-limit.ts`

### 4.5 Command Queue

**Source:** `src/process/command-queue.ts` (367 lines), `src/process/lanes.ts`

Lane-based FIFO queue that prevents concurrent agent runs from colliding:

```typescript
export const enum CommandLane {
  Main = "main",
  Cron = "cron",
  Subagent = "subagent",
  Nested = "nested",
}
```

**Architecture:**
- Per-lane configurable concurrency (`setCommandLaneConcurrency()`)
- Default Main lane: concurrency 1 (strict serial)
- Generation-based stale task filtering for SIGUSR1 restart recovery
- Gateway draining mode for graceful shutdown (`markGatewayDraining()`)
- `waitForActiveTasks()` with polling for clean shutdown
- `resetAllLanes()` preserves queued work after in-process restarts

> **Doc-Source Note:** The v1 doc described queue modes (`collect`, `steer`, `followup`, `steer-backlog`). These are higher-level auto-reply behaviors built on top of the lane system, implemented in the auto-reply layer rather than the command queue itself.

**Source:** `src/gateway/openai-http.ts` (19k)

The Gateway exposes an OpenAI-compatible `/v1/chat/completions` endpoint, allowing any OpenAI SDK client to use OpenClaw as a backend. Includes image budget tracking and session routing.

### 4.7 NEW: OpenResponses HTTP API

A separate HTTP interface implementing the OpenAI Responses protocol with extended streaming and tool support.

### 4.8 NEW: Config Hot-Reload

Live configuration reloading without gateway restart. File watcher detects changes, validates the new config, and applies it in-place. Startup writes (generated tokens, seeded origins) are filtered by hash to avoid restart loops.

## 5. The Agent Loop — How a Message Becomes Action

### 5.1 Intake & Routing

```
Inbound message -> Channel Bridge -> Session Resolution -> Command Queue -> Agent Runtime
```

1. **Channel bridge** normalizes the message (sender, content, attachments, thread context)
2. **Session manager** resolves to a session key based on `dmScope` rules:
   - `main`: all DMs share a single session
   - `per-peer`: isolated by sender ID
   - `per-channel-peer`: isolated by channel + sender (recommended)
   - **NEW: `per-account-channel-peer`**: isolated by account + channel + sender
   - `global`: single shared session for entire agent
3. **Command queue** serializes the run in the appropriate lane

### 5.2 Prompt Assembly

**Source:** `src/agents/system-prompt.ts`, `src/agents/pi-embedded-runner/system-prompt.ts`

OpenClaw builds a custom system prompt for every agent run:

```
System Prompt =
    Identity line (agent name + owner)
  + Authorized senders section
  + Current date/time (timezone-aware)
  + Reply tags (native reply/quote mechanism)
  + Messaging section (channel routing + message tool guidance)
  + Voice (TTS) capabilities
  + Skills index (compact metadata list)
  + Memory section (citations + retrieval hints)
  + Documentation pointers
  + Runtime metadata (host, OS, shell, agent ID, capabilities, repo root)
  + Tooling section (tool descriptions + usage patterns)
  + Workspace notes
  + Sandbox info (container/sandbox guidance)
  + -- Context Files --
  + AGENTS.md (operating instructions)
  + SOUL.md (persona/tone)
  + TOOLS.md (local tool notes)
  + IDENTITY.md (agent name/vibe)
  + USER.md (user profile)
  + HEARTBEAT.md (periodic task checklist)
```

**Prompt modes:**
- `"full"` — all sections (main agent, default)
- `"minimal"` — reduced sections for subagents (no memory, owner, messaging, voice, docs)
- `"none"` — just identity line (internal/test use)

**Key design decisions:**
- Bootstrap files truncated at configurable max chars (default 20,000)
- Context files are security-scanned (invisible Unicode, prompt injection, credentials) and truncated (20K chars, 70/20 head/tail ratio)
- Skills listed as metadata only — model reads full SKILL.md on demand
- Time is timezone-only for prompt cache stability

### 5.3 Model Inference & Streaming

**Source:** `src/agents/pi-embedded-runner/model.ts`, `src/agents/pi-embedded-subscribe.ts`

**Provider resolution cascade:**
1. User override (session-level model)
2. Agent default (agent-specific model)
3. Global default (from config)
4. Fallback (claude-sonnet-4.6)

**Transport APIs supported:**
- `anthropic-messages` — Anthropic SDK (with prompt caching)
- `bedrock-converse-stream` — AWS Bedrock
- `google-generative-ai` — Google Gemini
- `openai-responses` / `openai-codex-responses` — OpenAI
- `azure-openai-responses` — Azure OpenAI
- `github-copilot` — GitHub Copilot
- `ollama` — Ollama local
- Custom provider transports via plugins

**Auth profile management:**
- Multiple auth profiles per provider
- Last-good tracking with cooldown expiry
- Round-robin ordering
- OAuth token refresh fallback
- **NEW:** Configurable rate-limit retry count before cross-provider fallback (`auth.cooldowns.rateLimitedProfileRotations`)

**Streaming architecture:**
- Block chunking via `EmbeddedBlockChunker` (splits into paragraphs, code blocks)
- Reasoning/thinking parsed from `<thinking>`, `<thought>`, `<antthinking>` tags
- Reasoning modes: `"off"` (stripped), `"on"` (included), `"stream"` (streamed separately)
- `NO_REPLY` sentinel token filtered from outgoing payloads
- Messaging tool deduplication (prevents double-delivery)

**NEW: LLM Idle Timeout** (`src/agents/pi-embedded-runner/run/llm-idle-timeout.ts`)
- Default 60s timeout if no token received during streaming
- Wraps the stream async iterator with `Promise.race` against a timeout
- Configurable via `agents.defaults.llm.idleTimeoutSeconds`

### 5.5 NEW: Tool Loop Detection

**Source:** `src/agents/tool-loop-detection.ts` (624 lines)

Prevents the agent from getting stuck in infinite tool call loops:

**Four detector types:**
| Detector | What It Catches |
|----------|----------------|
| `generic_repeat` | Same tool + same args called repeatedly |
| `known_poll_no_progress` | `process.poll`/`process.log`/`command_status` returning identical results |
| `global_circuit_breaker` | Any tool repeated with no progress beyond threshold |
| `ping_pong` | Alternating between two tool call patterns with no progress |

**Thresholds:**
- Warning at 10 repetitions — injects nudge message
- Critical at 20 repetitions — blocks execution
- Global circuit breaker at 30 — hard stop

**Implementation:** Maintains a sliding window of last 30 tool calls with SHA-256 hashes of arguments and results. Outcome hashing allows detection of no-progress loops even when calls succeed.

## 6. Memory Architecture — How a Stateless Model Remembers

### 6.1 The Memory Stack

```
+-------------------------------------------+
| Layer 4: Semantic Vector Search            | <- "Find related notes even when
| (SQLite + embeddings, hybrid BM25+vector)  |    wording differs"
+-------------------------------------------+
| Layer 3: Long-term Memory (MEMORY.md)      | <- Curated insights, decisions,
| (manually maintained)                      |    preferences
+-------------------------------------------+
| Layer 2: Daily Logs (memory/YYYY-MM-DD)    | <- Raw daily notes, append-only
| (auto + manual)                            |
+-------------------------------------------+
| Layer 1: Session Context                   | <- Current conversation in the
| (JSONL transcript)                         |    model's context window
+-------------------------------------------+
```

### 6.2 Workspace Files as Memory

**Source:** `src/agents/memory-search.ts`, `src/auto-reply/reply/memory-flush.ts`

- **`memory/YYYY-MM-DD.md`**: Daily log files. Today + yesterday loaded at session start.
- **`MEMORY.md`**: Curated long-term memory. Only loaded in DM sessions (never group — security boundary).
- **`AGENTS.md`**: Operating instructions, injected every session.
- **`SOUL.md`**: Persona and boundaries, injected every session.

### 6.3 Vector Memory Search

**Source:** `src/agents/memory-search.ts`

**Embedding providers** (expanded from v1):
1. Local GGUF model via node-llama-cpp (~0.6 GB)
2. OpenAI `text-embedding-3-small`
3. Google Gemini (supports multimodal — images/audio alongside text)
4. **NEW:** Voyage
5. **NEW:** Mistral
6. **NEW:** Ollama (local, explicit config)

**Hybrid search (BM25 + Vector):**
- Vector similarity + BM25 keyword matching
- Configurable weights (default: 70% vector, 30% BM25)
- FTS tokenizer options: `unicode61` or `trigram`

**NEW: Advanced search features:**
- **MMR (Maximal Marginal Relevance)**: Diversity-based re-ranking (disabled by default)
- **Temporal decay**: 30-day half-life, recent memories rank higher (disabled by default)
- **Result caching**: Configurable max entries
- **Min score threshold**: 0.35 default

**Chunking:** ~400 tokens, 80-token overlap. File watcher with 1.5s debounce for incremental updates.

**NEW: Session memory search** (experimental, opt-in via `memorySearch.experimental.sessionMemory`):
Indexes JSONL session transcripts for cross-session recall.

**NEW: Remote embedding batch mode:**
Async batch processing with configurable concurrency (2 default), poll interval (2s), and timeout (60m).

### 6.4 Pre-Compaction Memory Flush

**Source:** `src/auto-reply/reply/memory-flush.ts`

When approaching context limits:
1. Silent memory flush turn fires
2. Model writes important context to `memory/YYYY-MM-DD.md`
3. Model replies `NO_REPLY` (user never sees this turn)
4. **NEW:** SHA-256-based context deduplication prevents duplicate memory entries within same compaction cycle
5. Auto-compaction proceeds safely

## 7. Session Management

### 7.1 Session Keys & Routing

**Source:** `src/sessions/session-key-utils.ts` (194 lines)

```
Direct messages:  agent:<agentId>:<channel>:direct:<userId>
Group chats:      agent:<agentId>:<channel>:group:<groupId>
Channels:         agent:<agentId>:<channel>:channel:<channelId>
Threads:          <baseKey>:thread:<threadId>
Cron jobs:        agent:<agentId>:cron:<key>:<runId>
Sub-agents:       agent:<agentId>:subagent:<subagentId>:...
ACP sessions:     agent:<agentId>:acp:...
Global:           global (single shared session)
```

### 7.2 Session Lifecycle

- **Daily reset**: default 4:00 AM local time
- **Idle reset**: optional `session.reset.idleMinutes`
- **Manual reset**: `/new` or `/reset`
- **NEW: Session write locks** — prevents concurrent writes to same session
- **NEW: Transcript repair** — automatic repair of corrupted/incomplete JSONL
- **NEW: Identity linking** — link identities across channels via `session.identityLinks`

### 7.3 Persistence

- **Transcripts**: JSONL files at `~/.openclaw/agents/<agentId>/sessions/<sessionId>.jsonl`
- **Store**: `sessions.json` — map of `sessionKey -> {sessionId, updatedAt, ...}`
- **ACP sessions**: Max 5,000 with 24-hour idle TTL, round-robin eviction

### 7.4 Session Maintenance & Pruning

**NEW:**
- **Mode**: `warn` (default) or `enforce` (automatic cleanup)
- **Pruning policy**: `pruneAfter: "30d"`, `maxEntries: 500`
- **CLI**: `openclaw sessions cleanup --dry-run`

### 7.5 Context Window & Compaction

**Source:** `src/agents/compaction.ts`

**Constants:**
- `BASE_CHUNK_RATIO = 0.4` — fraction of context to summarize
- `MIN_CHUNK_RATIO = 0.15` — minimum chunk size
- `SAFETY_MARGIN = 1.2` — 20% buffer for token estimation inaccuracy

**Compaction process:**
1. Token estimation via `estimateTokens()`
2. Tool result sanitization — `stripToolResultDetails()` removes untrusted details
3. Tool use/result pairing repair — `repairToolUseResultPairing()`
4. Multi-part summary generation via auxiliary LLM call
5. Identifier preservation (strict/custom/off policy for UUIDs, hashes, IDs, tokens)
6. Merge summaries instructions preserve: active tasks, batch progress, last request, decisions, TODOs

**NEW: Overflow compaction loop** — automatic retry-based compaction during token overflow with multiple attempts before fallback to truncation.

**NEW: Compaction safety timeout** — prevents runaway compaction from blocking the agent.

### 8.3 Gating

## 18. What Makes This Architecture Interesting (For Architects)

### 18.1 The Statefulness Problem

LLMs are stateless functions. OpenClaw makes them stateful through:
- **File-based memory** surviving process restarts
- **Session transcripts** (JSONL) replaying conversation history
- **Pre-compaction memory flush** extracting durable knowledge before context loss
- **Vector search** enabling semantic recall across sessions
- **NEW: Session memory search** (experimental) for cross-session recall via FTS

### 18.2 The Context Window as a Resource

Context is finite and expensive. OpenClaw manages it like a cache:
- **Compaction** = eviction with summarization (structured identifier-preserving summaries)
- **Pruning** = trimming low-value data (old tool results)
- **Skills lazy loading** = demand paging for instructions
- **Bootstrap truncation** = size limits on injected files
- **NEW: Tool loop detection** = prevents context waste from stuck loops
- **NEW: Overflow compaction loop** = automatic multi-retry compaction

### 18.3 Single-Writer Architecture

The Gateway is a single-writer system per session. The command queue ensures:
- Only one agent run per session at a time (lane-based concurrency)
- No concurrent writes to session transcripts (write locks)
- Deterministic ordering of multi-channel messages
- **NEW: Generation-based stale task filtering** for crash recovery

### 18.4 The Workspace as Source of Truth

Plain Markdown files in a git-backable directory:
- Memory is human-readable and editable
- Version control gives audit trails
- No database to manage (SQLite for vector search only)
- Migration is `git clone` + config update

### 18.5 Defense in Depth

10+ security layers from gateway auth to env var sanitization. The trust model is explicit: one operator boundary per gateway, not multi-tenant. Hard enforcement (tool policy, sandboxing, exec approvals) over advisory guardrails (system prompt).

### 18.6 Plugin-First Extension Model

90 extension packages, 20+ hook types, plugin-registerable tools/methods/services. Adding a new channel or provider is a self-contained extension package — no core changes needed.
